# DoraMonitor 未来功能计划

> 状态：扩展基础、多 Kimi 官方额度、设备身份保护与本地目录传输已落地。额外 Kimi 账号在用量归属可靠前不启用估算；归属映射增强仍属未来工作。ZCode 仅保留 Token 用量统计，不启用官方额度功能。
> 实施必须遵循 [PRD](./product-requirements.md)、[目标架构](./architecture-refactor-plan.md) 和 [数据迁移方案](./data-migration-plan.md)。

## 1. 规划原则

- 先完成工具、账号和额度集成边界，再增加具体账号与工具；
- 新能力不得破坏现有用量、历史、隐私和多设备同步；
- 官方额度、推测容量和不可用状态必须明确区分；
- 多账号数据必须全程隔离，不能只在 UI 上复制卡片；
- 每项未来需求都有独立验收条件，可分阶段交付。

```mermaid
flowchart LR
    A[架构与数据契约] --> B[额度集成注册表]
    B --> C[多 Kimi 账号]
    B --> E[其他工具/账号额度]
    A --> F[同步 codec 与账号隔离]
    F --> C
    F --> G[可选本地目录传输]
```

## 2. FP-01：多 Kimi 账号额度监控

### 需求

- 同一台机器可配置并监控两个或更多 Kimi 账号；
- 前端仍按 Kimi Code 工具分组，在组内切换个人、工作等账号；
- 每个账号有稳定匿名 `accountKey` 与本机 label；
- 官方额度、采样、历史、最高值、缓存、校准和调度锚点按账号隔离；
- 多设备同步样本保留 accountKey，不能在 peer 合并时变成 default；
- 账号 home/profile/凭据引用仅保存在本机适配层，不上传、不出现在公开 DTO 中。

### 账号归属规则

- 能确定用量账号时，只计入对应用量与估算；
- 不能确定时必须标记 `unknown_account`；
- 不得把两个账号的 Token 合并后分别生成高置信度结果；
- 跨设备同一 accountKey 可表示同一逻辑账号，但需明确的账号映射配置，不能仅凭显示名猜测。

### 验收

- 两个账号可同时采样，窗口和重置互不影响；
- 一个账号刷新或凭据失败不影响另一个账号；
- 历史、校准和调度键均包含 accountKey；
- 账号 label 改变不会重写或复制历史；
- 未知账号归属不会被计入高置信度估算。

## 3. FP-02：额外账号用量归属映射

### 需求

- 为额外 Kimi/OpenAI 账号建立"会话/用量 → accountKey"的归属映射规则；
- 能确定归属的用量计入对应账号；不能确定的必须标 `unknown_account`，不得猜测；
- 映射可靠后，解除当前对额外账号的等效额度估算与校准禁用（见 [limitations §4](./limitations.md)）；
- 存储侧：本机 SQLite 行存已预留 `account` 列（见 [综合改进方案](./comprehensive-improvement-plan.md) D1），映射规则在采集/归一化层落地。

### 验收

- 映射启用后每条用量恰好归属一个账号或 unknown，不出现重复计入；
- 同一 accountKey 的历史、最高值与锚点在映射启用前后保持连续；
- 解禁后的等效估算不混入 unknown 归属的用量；
- 映射配置仅存本机，不进入同步载荷。

## 4. FP-03：其他工具与账号的额度扩展

### 需求

- 新工具通过 QuotaIntegrationRegistry 注册，不在应用服务中追加工具判断分支；
- 一个工具可对应多个账号，一个额度账户族也可对应多个工具；
- 每种集成声明 capabilities、窗口、账号发现与快照规范化；
- 用量采集、模型定价、额度归属和公开 DTO 保持独立；
- 新集成必须带契约测试、错误降级和文档。

### 验收

使用一个假想集成验证：只增加集成、注册和测试，不改 HTTP 路由结构、前端分类模型、其他额度客户端及历史 schema。

## 5. FP-04：多设备同步能力保持与增强

### 已实现能力

- SSH/SCP、WebDAV 与 Local Directory 三种共享存储方式；
- 日粒度用量、一分钟额度用量桶、额度样本和覆盖水位；
- 对端摘要缓存与离线降级；
- Windows ↔ Windows、Windows ↔ Linux、Windows ↔ WSL 等跨环境同步；
- 普通看板请求不联网，只读取本地 remote-cache；
- 不同步提示词、代码、项目名、会话正文或凭据；
- v1/v2 摘要混合读取、字段规范化和单文件错误隔离；
- 多账号样本按 device + tool + accountKey + window 保留身份；
- 随机持久化 `deviceId` 与同名冲突拒绝，避免 Windows/WSL 覆盖同一摘要。

### Local Directory Transport

- 两端配置同一个实际共享目录的各自绝对路径；
- 复用现有摘要、codec、去重、缓存和安全约束；
- 不开放端口，不需要公网服务器，但不是直连或 P2P；
- 只新增传输后端，不改变领域和页面；
- 已处理原子写入、坏文件隔离和 `deviceName + deviceId` 唯一性检查。

## 6. FP-06：哈希工作区同步（已落地，2026-11-01）

### 已实现能力

- 同步摘要 v3 新增 `wsDaily`（日 × 哈希工作区 → token 四分项/请求数/credits）与 `wsSalt`；
- 工作区键以共享盐 HMAC-SHA256 前 16 位哈希后出设备，**路径与项目名明文不进同步通道**（隐私红线不破）；
- 保留槽（`unknown`/`legacy`）以字面量传输，对端可正确标注"未知工作区"；
- 盐在摘要内携带：首台设备生成，其余设备发现对端盐不同即采纳并在下一轮重传，一个周期内全网收敛；
- 看板：工作区面板按设备选择展示（合并 = 本机 + `对端工作区 · xxxxxx`，可设置本机别名）；选中对端工作区时 Hero/KPI/区间卡/每日趋势切对端口径。

### 已知边界

- 哈希不可逆，但对可枚举候选路径可离线撞库——共享存储本身需受信（与现状一致）；
- 跨设备同路径（如 `/mnt/d/DoraMonitor` vs `D:\DoraMonitor`）哈希不同，不合并为一行，可各自设置别名；
- 对端工作区明细不含模型维度：选中对端工作区时，模型明细区显示本机同筛选数据并提示。

## 7. FP-05：同步拓扑与运维体验

### 后续改进

- 配置页明确选择 SSH、WebDAV 或 Local Directory；
- 启动时主动检查 deviceName 是否为空或与已知 peer 冲突（当前在同步时检查）；
- 提供独立连接测试和更完整的最近成功状态，但不自动操纵用户浏览器验收；
- 账号未知的用量归属映射仍需增强，不能被 peer 合并机制“自动认领”。

### 非目标

- 不强制实现设备间 P2P 直连；
- 不要求用户部署 DoraMonitor 中心计算服务；
- 不同步原始会话、凭据或多账号本地 profile 密钥；
- 不通过自动合并解决无法确定的账号冲突。

## 7. 建议优先级

| 优先级 | 项目 | 状态 | 原因 |
| --- | --- | --- | --- |
| P0 | 架构边界、存储契约与同步 codec | 已完成 | 所有后续能力的基础 |
| P1 | 多 Kimi 账号官方额度 | 已完成 | 验证 accountKey 和归属隔离设计 |
| P1 | deviceName 冲突检测 | 已完成 | 避免 Windows/WSL 数据覆盖 |
| P2 | Local Directory Transport | 已完成 | 同机 Windows/WSL 无需服务器 |
| P2 | 额外账号用量归属映射（FP-02） | 待实施 | 解禁额外账号等效估算的前提 |
| P2 | 其他工具/账号额度与归属映射 | 待实施 | 在两类集成验证后推广 |
| P2 | 哈希工作区同步（FP-06） | 已完成 | 合并视图支持工作区维度且不泄露路径 |

每个优先级项独立提交和验收；调研确认数据源不可用时，应明确停止对应集成，而不是用不可靠数据补 UI。
