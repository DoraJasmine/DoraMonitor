# 阶段 3 实施方案：日聚合桶（Day-Bucket）架构

> 状态：**方案 v2（未实施）**。v1 经复审后重写，修订记录见 §9。
> 性能路线图：阶段 1（按文件增量缓存）与阶段 2（次级开销清理）已上线。

## 1. 要解决的问题

阶段 1 落地后，**服务进程存活期间**的加载成本已与历史数据量无关。仍有两个
与数据量线性相关的残留成本：

| 残留成本 | 现状 | 规模 |
| --- | --- | --- |
| **冷启动** | 服务重启后第一次扫描必须重读、重解析全部历史文件（当前 ~700ms） | 与磁盘历史总量成正比 |
| **常驻内存** | 所有原始记录（当前 ~9k 条）永久驻留，供聚合与"最近请求"使用 | 与记录总数成正比 |

codex 历史已达 577MB 且持续增长。历史涨到几 GB、记录到几十万条时，冷启动会回到
数十秒——增量缓存解决不了这个问题，因为它缓存的是**解析结果**，而解析结果本身
就在随数据量增长。

## 2. 目标与非目标

**目标**

1. 冷启动只解析"上次之后变化过的文件"——理想情况接近 0 文件。
2. 常驻内存有界：原始记录只保留一个有界窗口，更早数据只以聚合形式存在。
3. 聚合数值与全量解析一致（浮点求和顺序差异容差 ≤1e-9 CNY，见 §8-5）。
4. `/api/*` 响应形状对前端零改动。

**非目标**

- 不引入数据库（保持"两个运行时依赖"的离线打包约束；桶就是 JSON 文件）。
- 不改计价逻辑（pricing.js 原样复用）。
- 不做 provider 扫描异步化（桶落地后阻塞窗口只剩变化文件，通常 <50ms）。

## 3. 核心设计（v2：桶覆盖全历史，聚合一律从桶算）

### 3.1 两个数据层

```
                 ┌─ 原始记录层（内存，有界）────────────────┐
 scan 变化的文件▶ │ 近 30 天 records + events                │──▶ recent 表
                 └──────────────┬──────────────────────────┘      （唯一消费者）
                                │ 每文件解析后立刻折算
                                ▼
                 ┌─ 日聚合桶层（内存 + 磁盘持久化）──────────┐
                 │ 用量桶:  day → tool → model               │──▶ 全部聚合
                 │   → {i,o,cr,cc,req,credits,costCny,      │    (today/7d/30d/
                 │      costEstimated}                      │     all/热力图)
                 │ 事件桶:  day → name → count               │──▶ toolEvents
                 └───────────────────────────────────────────┘
```

**与 v1 的关键区别**：桶覆盖**全部历史**（含近 30 天），四个范围
（today/7d/30d/all）的聚合**一律从桶算**，原始记录只服务"最近请求"表。
v1 的"窗口前用桶、窗口内用原始记录再合并"方案有两个缺点，已放弃：
合并路径要处理 dailyByModel 跨源 top-6 选择，复杂且易错；30d 滚动窗口与
日历日的边界缝隙需要特判（见 §8-1）。

桶结构（每个源文件一个）：

```js
{
  version: 1,
  priceFingerprint: "sha1:…",      // 价格表指纹，见 §3.5
  tzOffset: -480,                  // 折算时的本地时区偏移，见 §3.6
  source: "sessions/wd_x/…/wire.jsonl",  // 相对 home，仅诊断
  stamp: { mtimeMs: 0, size: 0 },
  usageDays: { "2026-10-24": { "kimi-code": { "kimi-k3.1-pro": {
      i: 1200, o: 300, cr: 98000, cc: 100, req: 4, credits: 0,
      costCny: 0.234, costEstimated: false } } } },
  eventDays: { "2026-10-24": { "WebSearch": 3 } }   // 仅 kimi-code 有
}
```

- `usageDays` 折算规则与 `sync.js` 的 `buildSummary` 同构，外加 costCny /
  costEstimated（任一记录 estimated 则该桶格 estimated）。
- **事件也要桶化**（v1 遗漏）：`tool.call` 事件目前全量驻留内存且
  `toolEvents` 按范围计数——不桶化就仍是无界增长点。事件桶 = `day×name 计数`；
  无时间戳的事件计入 `"__none__"` 日（与现状一致：只被 "all" 统计）。

### 3.2 全部工具统一走桶

zcode/claude-code 等虽然扫描便宜，也统一折算进桶（折算是对已有记录的 O(n)
哈希累加，毫秒级）。理由：聚合层只有一条代码路径，不为"三个大头 + 四个小工具"
写两套合并逻辑。磁盘持久化同样全量（小工具桶文件极小）。

### 3.3 聚合入口（aggregate.js 新增，旧函数保留供测试对照）

```js
aggregateFromBuckets({ usageBuckets, eventBuckets, range, nowMs, tool })
```

- 产出与 `aggregate()` 完全同形：`{totals, daily, dailyByModel, models,
  recent, recentTotal, recentLimit, cacheHitRate}`，但 **`recent` 字段由
  调用方从原始记录窗口单独注入**（桶里没有明细）。
- `dailyByModel` top-6：桶里先算全时期 per-model totals 排名，取前 6，
  其余进"其他模型"——单源数据，无跨源合并。
- 热力图：从桶的 daily 数据构建（时间 0 的记录落 "1970-01-01" 桶，天然落在
  53 周单元格之外——与现状一致）。

### 3.4 桶的存放与生命周期

- 磁盘：`~/.doramonitor/buckets/<toolId>/<sha1(relPath)>.json`（原子写：
  tmp + rename；损坏 → 静默删除重折算；version 不符 → 丢弃）。
- 读时机：扫描某文件前查内存桶；内存没有 → 读磁盘桶并校验
  `stamp + priceFingerprint + tzOffset`；全部一致 → 复用（零解析）；
  否则解析文件 → 折算新桶 → 写盘。
- 失效（`collect.invalidate()` 追加）：内存桶全清；磁盘桶靠三重校验自然失效
  （源文件被删 → 读取时源不存在 → 丢弃）。
- 写放大评估：活跃会话追加 → 每 15s 扫描重折算该文件的桶并原子写一次，
  KB 级写入，可忽略。

### 3.5 计价指纹（priceFingerprint）——v1 的盲点

桶里存了 `costCny`，而价格表随厂商调价变化（如本次 K3.1 Pro 挂牌）。靠
人工 bump `version` 一定会漏。方案：**桶头存价格表指纹**——

```js
sha1(JSON.stringify(listPrices({})))   // 覆盖全部 id/数值/estimated/period
```

加载桶时指纹不匹配 → 该桶作废重折算。折算的输入是文件的解析记录（阶段 1
的文件缓存），重折算**不需要重读磁盘文件**；只有文件缓存也没有时才重解析。
自定义价格（customPrices）与 fxRate 变更继续走现有 `invalidate()` 全清路径
（它们不在指纹里，因为影响所有桶且用户操作低频）。

### 3.6 时区（v1 低估的风险）

桶按**本地日**折算（`dayKey` 现行语义）。v1 说"与现状相同"——不准确：
现状每次请求都从原始记录重算 dayKey，改时区立即自愈；持久桶会把折算时的
时区**冻结**。方案：

- 桶头存 `tzOffset`；加载时不匹配当前时区 → 桶作废重折算（同样优先从文件
  级缓存重算，免重读磁盘）；冷启动且无缓存 → 重解析一次（旅行场景，罕见，
  可接受）。跨时区漫游的日常代价 = 一次全量重折算，正确性无损。

## 4. 语义变更（需要拍板的决策点）

**7d / 30d 从"滚动小时窗口"改为"日历日窗口"（推荐，含今天）。**

现状 `rangeStart`：7d = now − 7×86400s（在当天中间切割）；桶只有日粒度，
无法复现半天切口。改为日历日后的差异：

| 范围 | 现状 | 桶化后 | 影响 |
| --- | --- | --- | --- |
| today | 本地当天 0 点起 | 不变 | 无 |
| 7d | now−7×86400s（半天切口） | 最近 7 个本地日（含今天） | 边界日最多多算 ~半天数据 |
| 30d | now−30×86400s | 最近 30 个本地日 | 同上 |
| all | 全部 | 不变 | 无 |

推荐接受：对用户"近 7 天"按日历日理解更自然，热力图/每日趋势本来就是日历
口径；`buildHeatmap` 与 `dailyByModel` 现有行为不受影响。若不可接受，
退回 v1 的双源合并方案（复杂度高，不推荐）。

## 5. "最近请求"表的语义（明确公示）

- 原始记录窗口默认 **30 天**（`RECORD_WINDOW_DAYS`）+ 次级上限
  **20,000 条**（防单日爆发场景内存失界；`recent` 取最新 500 条，两者不冲突）。
- 长期不用的用户会看到"最近请求"比历史少——在页脚/表格加一行说明
  "明细仅保留近 30 天"；**所有统计数字不受影响**（都来自桶）。
- `recentTotal` 与分页逻辑不变。

## 6. 多设备同步的衔接

- peer 摘要（`days→tool→model`）与桶同构。peer 合并改为把摘要折算成
  **内存桶**（不落盘）参与聚合——`summaryToRecords` 保留用于 recent 展示。
- DeepSeek 的 peer 费用按"当天 12:00"判峰谷的既有近似保持不变。
- peer 桶不参与价格指纹校验的失效（费用在合并时按当前设置现算）。

## 7. 实施步骤（每步独立可测试、可回滚）

| 步骤 | 内容 | 工作量 |
| --- | --- | --- |
| 1 | `src/buckets.js`：fold/merge/指纹/tzOffset；单测（折算 vs aggregate 逐字段一致） | 0.5 天 |
| 2 | 磁盘持久化：原子读写、三重校验、损坏容忍；单测 | 0.5 天 |
| 3 | 采集层接入：变化文件折算、未变化复用；`RECORD_WINDOW_DAYS` 裁剪（**裁剪前先折算**）；事件桶；单测（冷启动 0 重读、窗口边界无丢失、时区重折算） | 1 天 |
| 4 | `aggregateFromBuckets()` + server 切换 + **等价性大测试**：随机 3 工具 × 多文件 × 跨月数据，两条路径 totals/daily/models/heatmap/toolEvents 深度相等（容差 1e-9）；现有测试全绿 | 1 天 |
| 5 | 观测与上线：meta 加 `bucketHits/bucketMisses`；页脚显示冷启动耗时；真实数据费用/token 总和对比 | 0.5 天 |

**回滚开关**：`DORAMONITOR_DISABLE_BUCKETS=1` → 走现有"全量解析"路径
（阶段 1 的增量缓存不受影响）。实施期间两条路径并存，等价性测试随时对跑。

## 8. 复审发现的问题与修订记录

| # | v1 的问题 | 严重度 | v2 处理 |
| --- | --- | --- | --- |
| 1 | 7d/30d 是滚动小时窗口，日粒度桶无法复现半天切口——v1 完全没提 | **设计级** | §4 决策点：改日历日窗口（推荐）或退回双源合并 |
| 2 | **tool.call 事件没有桶化**——联网搜索统计仍无界增长，内存目标落空 | **设计级** | §3.1 eventDays |
| 3 | 价格表变更（厂商调价很频繁）靠人工 bump version 必然漏 | 高 | §3.5 价格指纹自动失效 |
| 4 | 时区变化：v1 称"与现状相同"——错误，持久桶会冻结折算时区 | 高 | §3.6 tzOffset 校验 + 重折算 |
| 5 | 承诺"逐位一致"不成立：桶求和顺序与逐条求和的浮点顺序不同 | 中 | 目标改为容差 ≤1e-9 CNY；等价性测试按容差断言 |
| 6 | recent 窗口语义变化未公示；单日爆发可击穿"按天数"的内存界 | 中 | §5 公示 + 20k 条次级上限 |
| 7 | 只桶化三个大头 provider → 聚合层两套合并逻辑 | 中 | §3.2 全工具统一 |

## 9. 预期效果

| 指标 | 阶段 2 现状 | 阶段 3 之后 |
| --- | --- | --- |
| 页面加载（进程存活） | <100ms | <100ms（不变） |
| **冷启动首次加载** | ~700ms（随数据线性涨） | **~50ms**（桶命中时零文件读取） |
| 常驻内存 | 全部原始记录+事件 | 30 天记录（≤20k 条）+ 全部桶（约为原始体积 1/50） |
| 数据量增长的影响 | 冷启动线性变慢 | **无影响** |
