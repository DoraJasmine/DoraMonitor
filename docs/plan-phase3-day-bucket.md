# 阶段 3 实施方案：日聚合桶（Day-Bucket）架构

> 状态：**方案（未实施）**。这是性能改造路线图的第三阶段，前两个阶段
> （按文件增量缓存 + 次级开销清理）已上线。本文是实施前的设计文档，
> 实施时应随代码变更同步更新。

## 1. 要解决的问题

阶段 1 落地后，**服务进程存活期间**的加载成本已经与历史数据量无关（增量缓存）。
但仍有两个和数据量线性相关的残留成本：

| 残留成本 | 现状 | 规模 |
| --- | --- | --- |
| **冷启动** | 服务重启后第一次扫描必须重读、重解析**全部**历史文件（当前 ~700ms，随数据增长） | 与磁盘上历史总量成正比 |
| **常驻内存** | 所有原始记录（当前 ~9k 条）永久驻留内存，供"最近请求"表和聚合使用 | 与记录总数成正比 |

今天 700ms 无感；当 codex/dsh 历史涨到几个 GB、记录到几十万条时，冷启动会回到
数十秒，内存占用数百 MB——阶段 1 的增量缓存对此无能为力，因为它缓存的是
**解析结果**，解析结果本身就在随数据量增长。

## 2. 目标与非目标

**目标**

1. 冷启动只解析"上次冷启动之后变化过的文件"——理想情况下接近 0。
2. 常驻内存有界：原始记录只保留一个可配置的滑动窗口（默认近 30 天），
   更早的数据只以聚合形式存在。
3. 聚合结果与全量解析**逐位一致**（现有测试语义全部保持）。
4. 对 `aggregate.js` / `server.js` / 前端 **API 形状零改动**。

**非目标**

- 不做跨进程数据库（SQLite 等）——保持"两个运行时依赖"的离线打包约束；
  桶文件就是 JSON。
- 不改变"最近请求"表的语义——它只展示窗口内的原始记录（见 §6 的 UI 说明）。
- 不动计价逻辑（pricing.js 原样复用）。

## 3. 核心设计

### 3.1 两个数据层

```
                    ┌─ 原始记录层（内存，有界）──────────────┐
scan 变化的文件 ──▶  │  近 N 天的完整 records（recent 表用） │
                    └──────────────┬───────────────────────┘
                                   │ 每文件解析后立刻折算
                                   ▼
                    ┌─ 日聚合桶层（内存 + 磁盘持久化）───────┐
                    │  per-file: date → tool → model        │
                    │  → {i,o,cr,cc,req,credits,cost…}      │
                    └───────────────────────────────────────┘
```

- **桶（bucket）**：一个源文件对应的日聚合结果，结构：

  ```js
  {
    version: 1,
    source: "sessions/wd_x/session_y/agents/main/wire.jsonl", // 相对 home，仅诊断用
    stamp: { mtimeMs: 0, size: 0 },          // 与现有文件戳一致
    days: {
      "2026-10-24": {
        "kimi-code": {
          "kimi-k3.1-pro": { i: 1200, o: 300, cr: 98000, cc: 100, req: 4,
                             credits: 0, costCny: 0.234, costEstimated: false }
        }
      }
    }
  }
  ```

  折算规则与 `sync.js` 的 `buildSummary` 完全同构（i/o/cr/cc/req/credits），
  额外带 `costCny` 与 `costEstimated`（任一记录 estimated 则整桶 estimated）。

- **内存里的原始记录只保留近 N 天**（`RECORD_WINDOW_DAYS = 30`，可配置）。
  "今天/7d/30d" 的聚合和 recent 表直接用原始记录（与现在完全一样）；
  "all" 范围的聚合 = 近 N 天原始记录聚合 **∪** 更早部分的桶聚合。

### 3.2 桶的存放与合并

- 磁盘位置：`~/.doramonitor/buckets/<toolId>/<sha1(relPath)>.json`
  （文件名哈希避免路径非法字符；`source` 字段保留原路径供诊断）。
- 读写时机：
  - 扫描一个文件前先查内存桶；内存没有 → 尝试读磁盘桶并**校验 stamp**；
    stamp 一致 → 直接复用（零解析）；不一致 → 解析文件、重建桶、原子写盘。
  - 冷启动 = 内存桶空，磁盘桶全部命中时，**一次文件都不用读**。
- 合并语义：桶是**可交换的**（按日期/工具/模型累加），合并顺序无关——
  这消除了现有 fork 去重"先到先得"对文件顺序的依赖（去重发生在桶折算之前，
  仍在单次扫描内部完成）。
- 会话移动/删除：`collect.invalidate()` 现有的"清空一切"语义保持——
  桶缓存全清 + 磁盘桶在下次扫描时按 stamp 重建。删除的文件其磁盘桶成为
  孤儿（stamp 校验时源文件不存在 → 丢弃）。

### 3.3 聚合入口的改动（aggregate.js 新增一个函数，旧函数不动）

```js
// 新增：桶 + 近期原始记录 的统一聚合
aggregateWithBuckets({ recentRecords, buckets, range, nowMs, tool })
```

- `range ∈ {today, 7d, 30d}`：与现在一样只用 `recentRecords`（窗口 ⊆ 30 天）。
- `range = all`：
  - `models/daily/totals` = `aggregate(recentRecords)` ∪ 桶中日期 < 窗口起点的
    部分逐日合并（桶里有现成的 per-day totals，直接相加）；
  - `recent` 仍来自原始记录（上限 500 条，窗口内）；
  - `dailyByModel` 的 top-6 选择需要**全时期**的模型排名——先从桶里算全时期
    per-model totals，再与近期排名合并取前 6，其余进"其他模型"。
- **一致性守护**：`buildHeatmap` 同样吃合并后的 daily 数据。

### 3.4 与现有机制的衔接

| 现有机制 | 衔接方式 |
| --- | --- |
| `collect.invalidate()` | 追加：清内存桶 + 让磁盘桶失效（下次扫描按 stamp 重建） |
| 自定义价/汇率变更 | 走同一条 invalidate 路径 → 桶里存的是 `costCny`，必须重算 → 桶缓存全清（代价：一次全量重解析，与现在保存设置后的行为一致） |
| 多设备同步（sync.js） | peer 摘要**本身就是桶格式**——`summaryToRecords` 保留，但可以让 peer 也走桶合并路径（二期顺手做） |
| CLI daemon（cli.js） | `toolTotals` 的 month/7d 范围 ⊆ 30 天窗口，继续用原始记录；"all" 状态行改用桶 |
| provider 的按文件增量缓存 | **保留**——它是"哪些文件要折算进桶"的探针，桶是它上面的一层 |

## 4. 实施步骤（每步独立可测试、可回滚）

### 第 1 步：桶数据结构与折算（纯新增，半天）

- 新建 `src/buckets.js`：`foldRecordToDay()`、`mergeBuckets()`、
  `bucketFromRecords()`、`stampOf(path)`。
- 单测：折算与 `aggregate.js` 的 totals 逐字段一致（同一组记录分别走
  `aggregate` 与 `bucketFromRecords`，断言相等）。

### 第 2 步：磁盘持久化（半天）

- `readBucket/writeBucket`（tmp + rename 原子写）；损坏文件 → 静默删除重解析
  （与 catalog 缓存同策略）；`version` 不符 → 丢弃。
- 单测：写→读往返、stamp 校验、损坏容忍。

### 第 3 步：接入采集层（1 天，核心步骤）

- `collect.js`：快照增加 `buckets`（每 tool 的桶列表）；
  provider 扫描产出不变，`collect` 在扫描后为**变化过的文件**折算新桶、
  复用未变化文件的桶。
- `RECORD_WINDOW_DAYS` 裁剪：快照 `records` 只保留窗口内记录；
  **窗口边界上的记录在裁剪前先折算**（保证桶完整）。
- `invalidate()` 追加清桶。
- 单测：冷启动（预置磁盘桶）→ `meta` 显示 0 文件重读且聚合正确；
  裁剪窗口边界无丢失（构造一条恰好在第 30 天的记录）。

### 第 4 步：聚合入口与 server（1 天）

- `aggregateWithBuckets()`（§3.3）；`server.js` 的 `/api/summary` 换用之，
  API 响应形状不变。
- 等价性大测试：随机生成 3 个工具 × 多文件 × 跨月数据，断言
  "全量解析聚合" 与 "桶 + 窗口" 两条路径的 `models/daily/totals/heatmap`
  深度相等（容差 0）。
- 现有 130 个测试全部保持绿色。

### 第 5 步：上线与观测（半天）

- `meta` 增加 `bucketHits / bucketMisses`（磁盘桶命中数）；
  页脚 debug 行显示冷启动耗时。
- 灰度验证：真实数据上对比两条路径的费用总和、token 总和（应逐位一致）。

## 5. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 桶与实时解析结果不一致（计价规则变化后旧桶未失效） | invalidate 全清路径覆盖；`version` 字段随折算逻辑变更递增 |
| "全部历史"的 recent 语义变化让用户困惑 | recent 表加一行说明"仅展示近 30 天明细"；全时期统计数字不受影响 |
| 磁盘桶膨胀（每文件一个 JSON） | 单桶 KB 级；按 tool 分目录；提供 `doramonitor buckets --prune` 清孤儿（低优先级） |
| 窗口边界（第 30 天）记录被裁剪丢失 | 折算先于裁剪（§4 第 3 步），专项测试覆盖 |
| 时区：桶按本地日聚合，跨时区漫游会错日 | 与现状相同（`dayKey` 本地时区），桶存原始日期串，不引入新问题 |

## 6. 预期效果

| 指标 | 阶段 2 现状 | 阶段 3 之后 |
| --- | --- | --- |
| 页面加载（进程存活） | <100ms | <100ms（不变） |
| **冷启动首次加载** | ~700ms（随数据线性涨） | **~50ms**（只读桶 + 解析变化文件，基本不随数据量变化） |
| 常驻内存 | 全部原始记录 | 近 30 天记录 + 全部桶（桶约为原始记录体积的 1/50） |
| 数据量增长的影响 | 冷启动线性变慢 | **无影响** |

## 7. 明确不做 / 留待以后

- provider 扫描的异步化/worker 化（冷启动被桶解决后，同步扫描的阻塞窗口只剩
  "变化的文件"，通常 <50ms，优先级大幅下降）。
- dsh 原生 zstd 多帧流式解压（同样只剩增量场景，fzstd 够用）。
- peer 设备的桶化合并（二期）。
