# 阶段 3 实施方案：日聚合桶（Day-Bucket）架构

> 状态：**v3 已实施上线**（2026-10-25）。实测：冷启动 6.1s → 282ms（三 provider
> 零文件重读）；today 范围桶路径与全量解析路径逐位一致；等价性测试 146 项全绿。
> 实施中相对方案的增量发现见 §10 末尾。

## 1. 要解决的问题

阶段 1 落地后，服务进程存活期间的加载成本已与历史数据量无关。仍有两个与
数据量线性相关的残留成本：

| 残留成本 | 现状 | 规模 |
| --- | --- | --- |
| **冷启动** | 服务重启后第一次扫描必须重读、重解析全部历史文件（当前 ~700ms） | 与磁盘历史总量成正比（codex 已 577MB） |
| **常驻内存** | 所有原始记录（当前 ~9k 条）永久驻留 | 与记录总数成正比 |

增量缓存解决不了：它缓存的是解析结果，解析结果本身随数据量增长。

## 2. 调研：成熟项目怎么做（v3 新增）

| 项目 | 做法 | 对本方案的启示 |
| --- | --- | --- |
| **ccusage**（ccusage/ccusage，Claude/Codex/OpenCode 等多 CLI 用量工具，生态内最成熟） | **完全无状态**：每次调用重读全部 JSONL；费用**一律查询时计算**（token 数 × 当前价目表：LiteLLM 价格 JSON + models.dev + 内置历史价目，按事件时间戳匹配）；按**日历日/周/月**分块 | ① 查询时计价是成熟范式 → 桶**不存费用**，只存整数 token，价格表变更零失效（取代 v2 的指纹机制）；② 日历日窗口是生态惯例（支撑 §5 决策）；③ 它的教训（issue #13：价格源在线不可用时整个工具不可用）反证我们**内置价目表**的正确性，必须保持 |
| **kimicode-dashboard**（本项目上游） | 无任何持久化，每次请求全量重扫 | 无可借鉴；阶段 1 的增量缓存已领先上游 |
| **ActivityWatch**（成熟本地遥测） | SQLite 存原始事件、查询时聚合，无预聚合 | 原始事件量小（每天几百条）时可行；我们的量级（数万条+GB 级文件）需要预聚合——反证桶的必要性。SQLite 选型见 §4.6 |
| **TimescaleDB 连续聚合 / Prometheus recording rules**（时序数据库标准范式） | 原始数据 + **物化 rollup**（带失效窗口）+ **原始数据保留策略**（过期只留 rollup） | 与本方案"桶 + 30 天原始窗口"同构，验证方向正确 |
| **git index（stat-cache）** | mtime+size 只作**提示**；mtime 与索引写入同秒的条目（"racily clean"）强制内容复核 | §4.5 采纳同款防护：mtime 距扫描时刻 <2s 的文件下次强制重读 |

ccusage 另有一项**未采纳**的精细化：按事件时间戳匹配**历史价目**（旧用量按当时价格计费）。我们维持现状（全部按当前价目表），与现有行为及 sync.js 语义一致；列为未来选项。

## 3. 目标与非目标

**目标**

1. 冷启动只解析"上次之后变化过的文件"（桶全命中时零文件读取）。
2. 常驻内存有界：原始记录保留 30 天（次级上限 2 万条），更早数据只以桶存在。
3. 聚合数值与全量解析一致（浮点容差 ≤1e-9 元，§9 步骤 4 的等价性测试守护）。
4. `/api/*` 响应形状对前端零改动。

**非目标**：不引入数据库依赖（§4.6 论证）；不改 pricing.js 计价语义；不做扫描
异步化（桶落地后阻塞窗口只剩变化文件）。

## 4. 核心设计（v3）

### 4.1 两个数据层

```
                 ┌─ 原始记录层（内存，有界）────────────────┐
 scan 变化的文件▶ │ 近 30 天 records + events                │──▶ 仅"最近请求"表
                 └──────────────┬──────────────────────────┘
                                │ 每文件解析后立刻折算
                                ▼
                 ┌─ 日聚合桶层（内存 + 磁盘持久化）──────────┐
                 │ usageDays: day → tool → model → rateKey │──▶ 全部聚合与费用
                 │   → {i,o,cr,cc,req,credits}（纯整数）   │    （today/7d/30d/
                 │ eventDays: day → name → count           │     all/热力图）
                 └───────────────────────────────────────────┘
```

与 v2 的关键区别：**桶里没有费用**。费用在聚合时用当前价目表现算
（ccusage 范式）。价格表（vendor 调价）变更后，新价格自动回溯适用于全部
历史，零桶失效。

### 4.2 桶结构与 rateKey

```js
{
  version: 1,
  tzOffset: -480,                     // 折算时本地时区偏移（§4.4）
  source: "sessions/wd_x/…/wire.jsonl", // 相对 home，仅诊断
  stamp: { mtimeMs: 0, size: 0 },
  usageDays: { "2026-10-24": { "kimi-code": { "kimi-k3.1-pro": {
      std: { i: 1200, o: 300, cr: 98000, cc: 100, req: 4, credits: 0 } } } } },
  eventDays: { "2026-10-24": { "WebSearch": 3 } }   // 仅 kimi-code
}
```

`rateKey`（计价修饰类，解析时逐记录判定，取代"按时间戳在查询时判峰谷/长上下文"）：

| rateKey | 语义 | 查询时乘数（输入侧/输出侧） |
| --- | --- | --- |
| `std` | 标准档 | 1 / 1 |
| `peak` | DeepSeek 工作日峰时 | 1 / 1 |
| `off` | DeepSeek 谷时/节假日 | 0.5 / 0.5 |
| `long` | OpenAI 单请求输入 >272K | 2 / 1.5 |

费用 = Σ 桶格 `tokens/1M × price(model) × multiplier(rateKey)`。
`rateKey` 判定逻辑从 `pricing.js` 的 `deepSeekTimeOfUse` / `longContextPricing`
**重构出共享 helper**（`rateKeyFor(model, usage, time)`），杜绝两处逻辑漂移；
estimated 标记与自定义价格同样在查询时按现行规则推导（自定义价命中时按
现行 costForUsage 的覆盖语义复刻，见 §9 风险 1）。

### 4.3 查询时计价的一致性论证

- 现状：`aggregate()` 对每条记录求 `r.costCny` 之和；`r.costCny` 来自
  `costForUsage = Σ tokens/1M × price × multiplier`——对同一 (model, rateKey)
  是**线性组合**，故"逐条求和"与"按桶格汇总后乘价"在浮点上仅差求和顺序
  （容差 1e-9，等价性测试断言）。
- 自定义价格 / fxRate 变更：查询时生效，**不再需要任何桶失效**（v2 需要）。
- `collect.invalidate()` 保留，仅服务于原始记录层（文件移动/删除后 recent 表
  与重解析路径正确）。

### 4.4 时区

桶按本地日折算（`dayKey` 现行语义）。持久桶会冻结折算时的时区——桶头存
`tzOffset`，加载时不匹配当前时区 → 桶作废重折算（优先从文件级缓存重算，
免读磁盘；跨时区漫游代价 = 一次重折算，正确性无损）。

### 4.5 racy-mtime 防护（git index 同款）

mtime+size 相同不代表内容没变（同秒内追加、mtime 粒度）。规则：文件戳的
`mtimeMs` 距本次扫描 <2s → 本次可复用，但**下次扫描强制重读**。活跃会话
文件每 15s 本来就会变化，此防护堵的是"写回与 stat 同秒"的窄窗口。

### 4.6 存储引擎：JSON（每桶一个文件）而非 SQLite

| 维度 | JSON/桶（选定） | SQLite（node:sqlite） |
| --- | --- | --- |
| 依赖 | 零（符合离线打包约束） | Node 22.5+（providers 已可选依赖，但桶是主路径，降级复杂） |
| 崩溃安全 | tmp+rename 原子写；损坏 → JSON.parse 失败 → 重折算 | WAL 更强，但收益对 KB 级文件有限 |
| 可调试 | 明文可读 | 需工具 |
| 冷启动 | ~550 个小文件读（SSD 数十 ms） | 单文件 + 索引，略快 |

**重估触发条件**：桶文件数 >5000 或冷启动 >300ms 时再迁 SQLite（ActivityWatch
路线）。当前量级（wire 78 + codex 172 + dsh 45 + …）JSON 足够。

### 4.7 桶生命周期

- 磁盘：`~/.doramonitor/buckets/<toolId>/<sha1(relPath)>.json`；原子写；
  损坏/version 不符/tzOffset 不符 → 丢弃重折算。
- 读：内存桶 → 磁盘桶（校验 stamp+tzOffset）→ 解析文件折算。
- 写放大：活跃会话每 15s 重折算+原子写一个 KB 文件，可忽略。
- 失效：**仅** stamp / tzOffset / version 三种自然失效；价格表变更不失效
  （查询时计价）；源文件删除 → 读取时源不存在 → 丢弃。

## 5. 语义决策（证据支撑）

**7d/30d 从滚动小时窗口改为日历日窗口（含今天）**——v1 遗漏、v2 提出的决策点，
现由 ccusage（daily/weekly/monthly 全部日历分块）与本项目热力图/每日趋势的
既有日历口径双重支撑。影响：边界日最多多算半天数据；today/all 不变。
若不可接受则退回双源合并（复杂度高，不推荐）。

## 6. "最近请求"表语义

原始记录窗口 30 天 + 次级上限 20,000 条；界面上公示"明细仅保留近 30 天"，
**所有统计数字不受影响**（全部来自桶）。

## 7. 多设备同步衔接

peer 摘要（`days→tool→model`，纯 token 计数）与桶天然同构——折算成**内存桶**
（不落盘）参与聚合；`summaryToRecords` 保留用于 recent 展示；peer 费用按
现行"当天 12:00 判峰谷"的近似保持。

| 步骤 | 内容 | 工作量 |

| 4 | 采集层接入：变化文件折算、未变化复用；30 天窗口裁剪（**裁剪前先折算**）；事件桶；单测（冷启动 0 重读、窗口边界无丢失、时区重折算、racy 强制重读） | 1 天 |

## 10. 修订记录

- **实施后增量发现（2026-10-25 落地时）**：
  ① 桶键最初用原始模型 id 查价，路由码（qfmodel/dfmodel）全部落兜底
  估价——等价性随机测试逮住，改为桶存 `pricingKey`；
  ② 跨文件去重的 first-wins 归属会随文件变化漂移，解法 = mtime 序 +
  桶内持久化去重签名集 + 传播窗口重算（方案未预见，实施时补全）；
  ③ 贡献为空的归档/fork 复制品必须持久化空 records 标记，否则每次
  重启都重解析它们（冷启动 5.2s→282ms 的最后一环）；
  ④ 窗口内文件的贡献明细随桶持久化 + 加载后按现行价目重算
  （方案只承诺桶计数，实施扩展到 records，冷启动才真正做到零解析）；
  ⑤ estReq 估算计数折算时混入表行级成分导致价格表更新后标记不自愈
  ——v2 起只记时间性估算，表行级由查询时现算（gpt-6.1-sol 定价
  上线时发现并修复）。
- **v3（本次）**：调研 ccusage / 上游 / ActivityWatch / Timescale / git index 后：
  ① 桶去费用化，计价移到查询时（消灭 v2 §3.5 价格指纹与价格失效路径）；
  ② 引入 rateKey 四档把峰谷/长上下文折进桶键，保住查询时计价的完备性；
  ③ 采纳 git 的 racy-mtime 防护；④ 存储 JSON vs SQLite 给出决策表与迁移触发
  条件；⑤ 日历日窗口决策获得 ccusage 证据支撑；⑥ 步骤 1 前置共享 helper 重构，
  明确自定义价部分覆盖为最高风险点。
- **v2**：复审修正 7 处（7d/30d 语义、事件桶化、价格指纹、时区、浮点容差、
  recent 公示、全工具统一）。
- **v1**：初版（按文件缓存之上加日聚合层）。
