# DoraMonitor 项目需求文档（PRD）

> 状态：v1.0 草案，待项目所有者确认。
> 本文是功能、架构、数据迁移和验收的共同基线。历史待办与本文冲突时，以项目所有者最新确认的决定为准。
> 后续设计：[高内聚低耦合架构方案](./architecture-refactor-plan.md)、[数据兼容迁移方案](./data-migration-plan.md)、[未来功能计划](./future-roadmap.md)。

## 1. 背景与问题

DoraMonitor 已是本地、隐私优先的 AI 编码工具用量看板，覆盖用量、费用、额度、会话与多设备同步。
当前主要问题不是功能缺失，而是领域边界不统一：

- 前端和用量统计按 AI 工具分类，部分额度 API、状态和存储却按 `provider` 分类；
- `provider` 同时容易被理解为工具、额度账户族、模型厂商或配置供应商；
- 额度历史、采样和校准的前端调用依赖内部额度字段，造成前后端耦合；
- 在边界不清的情况下继续增加功能，会扩大兼容成本和数据迁移风险。

因此，下一阶段首先统一需求和领域语言，再实施架构与数据契约重构，而不是直接全局改名或推倒重写。

## 2. 产品愿景

让用户能够在本机准确、透明地理解 AI 工具用量与额度消耗，同时让维护者能够低风险地增加工具、模型、定价和额度能力。

产品必须长期坚持：

1. **工具是用户视角的主分类**；
2. **数据准确性优先于展示复杂功能**；
3. **估算必须说明依据、置信度和局限**；
4. **隐私与安全不能被新功能削弱**；
5. **升级不能丢失或重复用户历史数据**；
6. **架构服务于需求，不为拆层而拆层**。

## 3. 目标用户与核心场景

### 3.1 个人开发者

- 按工具查看今天、7 天、30 天和全部用量；
- 对比模型 Token、缓存命中和 API 刊例价等效费用；
- 查看 Kimi Code、Codex 的官方额度窗口与推测容量；
- 跨设备复原本机和 peer 的完整用量区间。

### 3.2 重度 AI 工具用户

- 识别额度消耗趋势、异常区间和估算波动；
- 查看每次测算的实际 Token、费用、额度增量、模型结构和缓存命中；
- 限定只使用 Kimi Code 或 Codex 客户端用量参与对应额度估算。

### 3.3 维护者与二次开发者

- 通过明确的工具注册和适配边界增加数据源；
- 在不理解内部额度账户族的情况下调用工具导向 API；
- 升级版本时获得可验证、可回滚的数据迁移；
- 用自动化测试验证采集、聚合、估算、存储和 API 行为。

## 4. 领域术语与分类约束

| 术语 | 含义 | 允许出现的位置 |
| --- | --- | --- |
| `tool` | AI 编码工具，如 `kimi-code`、`codex`、`omp` | 前端、路由、应用服务、公开 API、用量记录 |
| `quotaProvider` | 额度账户族，目前为 `kimi` 或 `openai` | 仅额度领域、额度存储及同步适配层 |
| `modelProvider` | 模型上游厂商，用于模型身份和定价 | 模型身份、定价和配置领域 |
| `accountKey` | 额度账号的稳定匿名标识，同一工具可有多个账号 | 额度领域与额度 API |
| `usageScope` | 参与额度估算的客户端范围 | 额度领域与额度 API |
| `window` | 额度窗口；Kimi/Codex 当前为 `session`（5 小时）或 `weekly`（7 天） | 额度领域与额度 API |

强制约束：

- 新增前端 quota 代码不得读取 `capacity.provider` 来决定页面分类；
- 新增公开应用 API 必须使用 `tool` 作为主分类参数，多账号时使用 `tool + accountKey`；
- 新代码不得再引入含义不明的裸 `provider`；历史配置供应商功能应按其真实语义单独命名；
- `tool` 与 `quotaProvider` 的转换只能发生在明确的应用/额度适配边界；
- 一个额度账户族未来可以对应多个工具，不得把一对一映射写死到所有领域函数中；
- 一个工具可以对应多个账号，样本、历史、最高值、校准和调度必须按 accountKey 隔离；
- 新工具额度通过集成注册表接入，并按 capabilities 声明窗口与功能，不得强行复用 Kimi 的 5h/7d；
- 用量无法确定账号归属时必须显式标记，不得合并后冒充各账号的高置信度样本。

## 5. 功能范围

### 5.1 本期必须保留并统一的能力

#### FR-01 工具导向的用量看板

- 按工具筛选用量，支持全部工具视图；
- 支持今天、近 7 天、近 30 天和全部范围；
- 展示输入、输出、缓存读取、缓存写入、请求量、模型分布、趋势和热力图；
- 工具不可用或数据损坏时，不影响其他工具展示。

#### FR-02 模型身份与计价

- 模型原始标识、解析标识和展示名称必须可追溯；
- 内部统一 CNY 账本，展示层再转换币种；
- 支持官方定价链接、自定义价格及明确的估算标记；
- 费用必须包含普通输入、缓存读取、缓存写入和输出，不得只按输入或输出计算；
- API 刊例价等效费用不得表述为真实账单。

#### FR-03 官方额度窗口

- Kimi Code 和 Codex 卡片按工具展示 5 小时、7 天额度与重置时间；
- 官方额度不可用时给出明确原因，不伪造零值；
- 额度采样和在线刷新失败不得影响其他页面。

#### FR-04 等效额度估算

- 估算结果必须明确标注为推测值，不代表官方固定额度或真实账单；
- 重置时间变化、额度百分比下降和无效区间不得形成跨重置消耗；
- 异常费用区间必须保守剔除，并公开剔除数量和质量影响；
- 等效金额主值使用加权总费用与加权总额度消耗之比，避免短区间中位数跳档；
- 普通测算是主结果，高置信度普通测算优先展示；
- 长程测算已退役，不再展示或定期执行；兼容计算、历史查询与既有数据保留；
- 5h 与 7d 独立采样、独立触发、独立记录，不得用一个窗口的触发条件替代另一个窗口；
- 估算缓存必须随算法版本失效，既有历史记录保持原值，不静默重算或改写。

#### FR-05 手动测算与历史

- 默认测算起点是上一次测算终点；
- “结束并立即测算”可直接续算上一段；
- 重设起点时，可用的上一段静默结算并写入历史，标明触发原因；
- 重置、样本不足、覆盖不完整或用量不足时不得写入伪造结果；
- 每批历史展示四个缓存档，并记录区间起止、实际 Token、费用、额度增量、缓存命中和分模型 Token；
- 历史链式关系、去重键和分页顺序在重构前后必须保持一致。

#### FR-06 客户端范围

- Kimi 支持全部客户端 / 仅 Kimi Code；
- Codex 支持全部客户端 / 仅 Codex；
- 开关只出现在额度页面；
- 跨客户端模型归属错误时必须标为未知或排除，不得混入其他厂商模型。

#### FR-07 会话与工作区

- 保留会话列表、安全预览、归档、恢复和删除能力；
- 高危操作必须有确认和路径穿越防护；
- 不得因用量或额度重构改变会话安全边界。

#### FR-08 多设备同步

- SSH/WebDAV 同步必须显式启用；
- 同步日粒度摘要、额度用量桶、额度样本和覆盖水位；
- 新旧版本 peer 可以短期共存，未知字段不得导致整个同步失败；
- 覆盖不完整的数据必须标记 provisional 或 pending，不得冒充 complete。

#### FR-09 CLI、部署与配置

- 保留 Web、status、daemon、sync、tools、stop 等命令；
- 保留 npm 安装、源码运行、后台启动和 Windows 自启；
- 保留设置、模型配置和目录检测；
- 设置保存和模型配置不得泄露凭据值。

### 5.2 本期不做的事情

- 不推倒重写所有采集器和聚合算法；
- 不为了“架构升级”强制引入数据库、Web 框架、TypeScript 或大型依赖；
- 不实现云账号体系、多人协作或远程公开服务；
- 不读取提示词、回复、代码、附件全文或 Provider 凭据；
- 不把估算结果包装成官方承诺；
- 不在一次提交中同时完成目录大迁移、存储改名、API 改版和算法调整。

## 6. 数据与兼容需求

### 6.1 必须兼容的数据

- `~/.doramonitor/quota-estimator/samples.jsonl`；
- `~/.doramonitor/quota-estimator/history.jsonl`；
- `~/.doramonitor/quota-estimator/state.json` 中的缓存、最高值、调度锚点和校准状态；
- `~/.doramonitor/config.json`；
- peer 摘要及本地 remote-cache；
- 浏览器中的合理用户偏好。

### 6.2 迁移硬性要求

1. 迁移前自动备份，备份未成功不得改写原文件；
2. 迁移必须原子、幂等，可从中断状态恢复；
3. 读取旧字段时先规范化，再参与去重，避免旧新记录形成两份历史；
4. 历史 `createdAt`、`calculationStartAt`、`calculationEndAt`、`previousCalculationEndAt` 和签名不得改变；
5. 调度锚点不得因字段迁移而意外重算或重复写入；
6. 迁移失败时继续使用旧数据只读运行，并给出可操作错误，不得清空状态；
7. 旧版本回滚时可以通过备份恢复，迁移过程不删除唯一副本；
8. 数据迁移与算法版本升级分开，不得借字段迁移改变历史估算数值。

### 6.3 API 兼容要求

- `/api/quota`、额度历史、采样历史和校准以 `tool` 为主参数；
- 旧 `provider` 参数在兼容期内由服务端适配，前端不再发送；
- 同时提供 `tool` 和旧 `provider` 且语义冲突时返回 400，不得静默选择一个；
- 响应必须始终包含明确的 `tool`；
- 兼容字段和删除时间必须写入 API 文档，不得无限期隐式双写；
- Tauri 预留调用的 payload 与 HTTP 契约保持同等语义。

## 7. 非功能需求

### 7.1 隐私与安全

- 默认仅监听 `127.0.0.1`，不开放 CORS；
- 只处理用量元数据，不处理会话正文和凭据值；
- 日志、错误、同步和测试 fixture 不得包含密钥；
- SQLite 保持只读，写文件采用原子替换和必要权限限制。

### 7.2 准确性与透明性

- Token 四分项、缓存命中和费用口径必须可测试；
- 估算结果必须能追溯到样本和实际用量；
- 置信度是数据质量评分，不是统计概率；
- 异常、外推、覆盖不足和数据不足必须可见，不能静默美化。

### 7.3 可靠性

- 单工具、单模型、单 peer 或单行坏数据不得拖垮全局；
- 定时任务失败保留锚点并允许重试；
- 无有效结果不得推进调度锚点；
- 迁移、采样、历史写入和状态保存必须考虑中断与重复执行。

### 7.4 可维护性与扩展性

- 采集、聚合、定价、额度、存储、HTTP 和 UI 各自职责清晰；
- 领域逻辑不得依赖 React 或 HTTP 参数形状；
- 文件系统与网络适配不得散落在估算算法中；
- 新增工具应主要通过注册和适配完成，不应要求复制页面级分类逻辑；
- 重构每一步保持可构建、可测试、可回退，避免长期分支和大爆炸提交。

### 7.5 性能与运行环境

- 保留采集缓存、日桶聚合和有界缓存策略；
- 常规页面打开不得触发完整历史重扫或写测算历史；
- 迁移只能执行一次，不得增加每次读取的全文件改写；
- 支持 Node.js 18+，推荐 22.5+；Windows 与类 Unix 行为一致；
- 无系统数据库、Rust 工具链或管理员权限依赖。

## 8. 验收标准

### 8.1 工具分类验收

- 前端额度相关代码不再用 `provider` 决定工具分类；
- 所有公开额度入口可用 `tool=kimi-code`、`tool=codex` 完成；
- 旧 `provider` 请求在兼容期内得到等价结果；
- 冲突参数返回明确 400；
- 模型配置中的供应商语义不被错误替换为工具。

### 8.2 数据迁移验收

- v1 samples/history/state fixture 迁移后字段、数量和顺序符合 v2 契约；
- 重复执行迁移不产生新增或重复记录；
- 新旧 peer 混合时去重结果一致；
- 历史续算起点、最高值和调度锚点保持连续；
- 模拟备份失败、写入中断和坏行时，原数据仍可恢复；
- 既有历史估算值不被重新计算。

### 8.3 产品回归验收

- 原有工具用量、价目、额度、会话、同步和 CLI 场景通过；
- 只展示并定期执行普通测算，旧长程锚点不会触发新任务；
- 相近总量与额度消耗不会仅因中位数跳档产生巨大估算差；
- `npm test`、`npm run build`、`npm pack --dry-run` 通过；
- 不通过浏览器自动化代替 API、迁移和领域逻辑测试。

## 9. 分阶段实施顺序

| 阶段 | 交付物 | 完成条件 |
| --- | --- | --- |
| P0 需求基线 | 本文及术语表 | 项目所有者确认范围与兼容策略 |
| P1 契约与保护测试 | API DTO、存储 schema、旧数据 fixture、特征测试 | 未改实现即可证明旧行为被覆盖 |
| P2 工具边界 | 前端/API 全面使用 `tool`，集中映射额度账户族 | 前端不再依赖 `capacity.provider` |
| P3 数据迁移 | v2 存储、自动备份、幂等迁移、peer 双读 | 旧数据无丢失、无重复、可回滚 |
| P4 模块解耦 | 应用服务、额度领域、存储和 HTTP 依赖单向化 | 领域测试不启动 HTTP/React |
| P5 成熟化 | 错误契约、日志、性能、文档和发布门禁 | 全量验收与迁移演练通过 |

每个阶段独立提交、独立验证；不在 P2 同时改变历史算法，不在 P4 同时改变产品功能。

## 10. 待确认决策及建议默认值

以下不影响先编写架构草案，但实施前需要确认：

1. **旧 `provider` API 兼容期**：建议保留一个 major 版本，下一 major 删除；
2. **迁移启动方式**：建议 Web 启动时自动迁移，先备份，失败则只读降级；
3. **旧历史数值**：已决定保持原值，不做离线重算；
4. **首页估算**：已决定普通高置信度结果为主，替代旧待办中的“只看长程”；
5. **技术栈**：建议保持 CommonJS、原生 Node HTTP、React 和 JSONL，先解决边界而非更换技术栈；
6. **Tauri**：建议保持 HTTP/invoke 同构契约，但本期不新增桌面壳实现。
