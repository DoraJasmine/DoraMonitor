# 额度估算逻辑说明

> 更新：2026-10-31。本文描述当前实现的端到端逻辑、代码位置与已知不足。
> 历史方案设计稿（含调研与取舍过程）见 git 历史。

## 0. 术语表（先读这个）

页面按 **AI 工具** 分类展示，而代码和存储里有三个容易混淆的概念：

| 概念 | 取值 | 用在哪 | 代码/存储里的字段名 |
| --- | --- | --- | --- |
| **工具** (tool) | `kimi-code`、`codex`、`claude-code`、`omp`、`gemini`、`zcode`、`qoder-cn`、`qoder-cn-cli`、`dsh` | 页面页签、用量采集、`/api/tools`、`/api/summary` 的 `tool` 参数 | `tool` |
| **配额账户族** (quota provider) | `kimi`、`openai` | 额度窗口归属、测算、样本/历史存储 | `quotaProvider`（v2）；`provider`（v1/兼容） |
| **模型供应商** (model vendor) | `kimi`、`openai`、`qodercn`、`alibaba` 等 | 定价表、模型识别 | `modelProvider` |

公开 API 和前端统一使用 `tool`，映射集中在 [quota-tool.js](../src/quota-tool.js)。
样本、历史和状态由 [quota-schema.js](../src/quota-schema.js) 双读规范化，[quota-migration.js](../src/quota-migration.js)
自动备份并原子迁移为 v2；键字符串、历史数值和调度锚点保持不变。三者的桥接关系：
`openai` 账户族 ⇔ `codex` 工具；`kimi` 账户族 ⇔ `kimi-code` 工具
（但"全部客户端"范围下其他客户端的 Kimi/GPT 模型用量也计入）。

## 1. 数据来源

- **额度采样**：Web 主进程每 60 秒（[quota-sampler.js](../src/quota-sampler.js)）拉取
  Kimi 官方额度接口和 Codex rate-limit 快照，按窗口（`session` 5 小时 / `weekly` 7 天）
  写入 `~/.doramonitor/quota-estimator/samples.jsonl`，去重键为
  `[provider, accountKey, window, sampledAt, source]`，保留 **90 天**。`usedPercent` 以 JSON 数值
  保存，代码不会强制取整；Kimi 官方目前提供整数百分比，因此精度主要受上游粒度限制。
- **用量记录**：本地采集（各工具的会话文件）+ 跨设备 peer 同步（WebDAV/SSH）。
  每条用量带 `tool`、模型、四种 token 类型、成本。
- **归属过滤**：[quota-models.js](../src/quota-models.js) 把用量按模型/工具映射到账户族；
  `usageScope`（全部客户端 / 仅 Kimi Code / 仅 Codex）决定"仅本工具"时其他客户端用量
  是否被记为 unknown。

## 2. 区间构建（[buildIntervals](../src/quota-estimator.js)）

相邻额度样本两两配对：`usedPercent` 严格增长即形成一个区间：

- `dp` = 额度消耗百分点；`usageBetween` 统计区间内分模型 token 与成本；
  额度不变（闲置）期间不产生区间，也不打断链条；同一时间戳的重复样本只保留最高已用百分比，
  非正时长区间不会进入估算或长程合并；
- **覆盖率**（`peerCoverage`）：peer 水位线落后于区间终点 → `pending`；peer 快照缺失
  或陈旧 → `provisional`；区间内 unknown 用量 >10% → `provisional`。旧版 peer
  （快照里没有 `quotaUsage`/`usageWaterMark`）不参与覆盖判定。

**长程区间**：`mergeLongIntervals` 把首尾相接的区间链合并，达到时长门槛即切分：
5 小时窗口 ≥30 分钟，7 天窗口 ≥6 小时。只使用自动采样（手动校准样本排除）。

## 3. 标准估算（[estimateWindow](../src/quota-estimator.js)）

先排除非有限数值、非正额度增量/时长和负成本区间；有效样本 = 覆盖率为
complete/provisional 且 token>0 的区间。至少 5 个有效费用样本时，对 `log(成本 / dp)` 计算中位数和
MAD（中位数绝对偏差），偏离中位数超过 `3.5 × max(1.4826 × MAD, 0.25)` 的区间会被剔除。
这只检测**每 1% 额度对应费用**的异常，不按 Token 总量删样本；最小尺度避免 MAD 为 0 时误杀正常波动。
拟合、局部估算和观测历史统一使用剔除后的区间，并通过 `outlierCount`、`outliers_excluded` 公开处理结果。

按缓存命中档 85/90/95/98% 各出一行，方法与置信度：

1. **拟合路径**（样本 ≥5 且跨度 ≥5%）：对各区间的"每 1% 额度的 token 构成"做非负最小二乘，
   得到分模型费率拟合；区间内命中率用 `interpolated`，外推档用 `extrapolated`。
2. **局部路径** `local`：命中率 ±2.5%（放宽 ±5%）邻域内的直接观测中位数。
3. **价格弱先验** `modeled`：没有足够 token 观测时，用区间成本 + 刊例价反推。
4. **insufficient**：以上都不可用，不编造数字。

**金额 → token 的两步换算**（用户视角的核心逻辑）：

1. `costCapacity`：按时间、额度跨度和区间时长计算权重，以 `Σ(权重 × 成本) / Σ(权重 × dp) × 100`
   得到 **等效人民币**（`api-list-price` 口径）。先聚合再相除，避免新增短区间时中位数跳档；
   各区间"烧完 100% 额度所需金额"的 25%/75% 加权分位数仅用于波动范围；
2. `tokensFromCost`：对指定命中率构造 1000-token 输入批次（缓存读按该命中率、缓存写入
   与输出比取自实际用量结构、按模型结构 mix 加权），用刊例价算出**每 token 综合单价**，
   金额 ÷ 单价 = **估算Token总量**。UI 上"估算模型"标注的就是这个结构。双档缓存写入按
   `docs/pricing.md` 的规则处理：TTL 已知时精确计价，未知时对未分类部分使用两档简单平均。

**置信度分数**（0–100）：样本数(≤25) + 跨度(≤20) + 覆盖率(complete 20 / provisional 8)
+ 方法分(4–15) + 拟合残差分(≤20) − 异常剔除扣分（每个 2 分，最多 10 分，总分最低为 0）。
provisional 只降分，不隐藏结果；剔除区间的详情会显示数量，质量原因包含 `outliers_excluded`。

## 4. 长程交叉校验

与标准估算同一套估算器，但输入只保留 ≥时长门槛的长程区间，且**没有样本数硬门槛**：
只要形成长程区间就可以计算校验结果，样本少时如实给低置信度。7d 需要 ≥6 小时的连续消耗链，
所以"下午有数据"不等于已有多个独立长区间；只有一两条链时置信度低是预期行为。

页面以高置信度普通测算为主，长程结果默认收起为次要交叉校验，不再与主结果争夺展示层级。
后台长程样本和独立历史仍保留；历史只由下面独立的 15% 触发写入，不会被另一个窗口的标准测算顺带写入。

## 5. 触发机制（谁会写一条测算记录）

| 触发 | 说明 |
| --- | --- |
| **标准定期调度** | 5h 和 7d 各有独立锚点：本窗口经过 ≥1 小时且额度增长 ≥4%，或增长 ≥10% 时触发。两个条件仍为或关系 |
| **长程定期调度** | 5h 和 7d 各有独立锚点：本窗口额度增长 ≥15%，同时满足 5h ≥30 分钟、7d ≥6 小时才触发 |
| **手动立即测算** | 额度页"设为测算起点 / 结束并立即测算"（`manual` / `manual-end`） |
| **校准** | 手动校准起止（`reanchor` 等） |
| **打开看板** | 只更新展示、缓存和有效最高纪录，不写测算历史；算法版本变化会立即使旧缓存失效 |

百分比下降或重置时间变化都会重新锚定，同一调度链的最小间隔为 5 分钟。定时失败或没有有效结果时
不前进锚点，下一分钟重试。历史以 `[provider, accountKey, usageScope, estimateKind, window, cacheHitRate]`
为键链式去重；没有新观测终点的定期目标不会重复写空批次。每条记录附 `observations`（本区间总 token、
成本、增量、分模型 token、缓存命中），旧记录明细为空时用留存样本按数据窗口重建。

## 6. 展示口径

- 页面按工具分卡片（Kimi 额度 / Codex 额度），卡内按窗口（5 小时 / 每周）分列；
- 首页按窗口独立选择**创建时间最新**的 `confidenceScore ≥95` 且 `fullWindowTokens` 有效的普通测算历史；当前重算低于 95 分时不会覆盖或清空最近一次合格历史，低分结果不显示估值，详情页仍保留完整历史；
- 每行：`以X%缓存命中计算：估算Token总量 · 估算金额 · 置信度 · 估算模型`；
- 普通测算是主结果；长程交叉校验默认收起，仅作次要参考；
- 置信度文案：高/中/低/数据不足；`sessionDerived`（×5 回退）已删除；
- 算法版本升级只使缓存失效并影响后续测算，已写入的历史记录保持原值，不回填或改写。

## 7. 目前的不足

1. **术语不一致**（见 §0）：存储与 API 用 `provider` 指配额账户族，页面按 `tool` 分类。
2. **7 天长程要求 ≥6 小时连续消耗链**：达到门槛即切分，不足门槛的尾巴丢弃；轻度使用者
   可能长期只有数据不足或低置信度结果。
3. **跨设备覆盖率依赖 peer 版本与同步新鲜度**：旧版 peer 被跳过；水位线落后时区间为 pending。
4. **额度百分比粒度**：Kimi 返回整数百分比，短区间噪声较大。
5. **accountKey**：Kimi 固定 `kimi:default`，多账号未区分；Codex 使用匿名哈希。
6. **模型结构取自观测**：缓存写入占比与输出比来自实际用量，极端样本可能使单价失真。
7. **调度参数硬编码**：标准的 1 小时 / 4% / 10%、长程的 15% 与最小 5 分钟间隔未暴露到设置。
8. **采样依赖 Web 主进程存活**：daemon 不写额度样本，Web 不在时无采样与调度。
9. **金额口径为 API 刊例价**，不是实际账单或厂商承诺的套餐 Token 上限。
10. **样本保留 90 天**：读取时过滤并每天原子压缩一次磁盘文件；更早的明细无法重建。
11. **跨客户端归属靠模型名识别**：新模型或改名模型在映射更新前可能被归为 unknown。
12. **本地原始记录有 30 天窗口和 20,000 条驻留上限**：极高用量下，较早区间可能只有部分
    原始记录；聚合日桶不能还原分钟级区间，不能把这类结果当作完整覆盖。
